Bloom

Intent-trading server · January 2026 to present

The problem

Indian brokers describe the same market differently. The NSE cash segment is nse_cm at Kotak, NSE_EQ at Upstox and Dhan, and two separate fields at 5paisa. Order states, timestamps and tick feeds disagree too. Anything built on them ends up special-casing brokers.

What I built

One URL and one payload for placing orders, reading books and streaming prices, whichever broker is behind the account. Around it: a per-instrument candle store, a Replay broker that trades history at up to 500x, a Svelte web app and an Android app. I'm porting the backend from Python to Rust route by route.

Flow

Durable graph-flow engine · June 2026 to present

The problem

A trading workflow that dies halfway can leave orders and positions in an unknown state. A backtest that shares code paths with live trading can also, by accident, reach a real broker.

What I built

An engine that compiles YAML graphs into levels and checkpoints each node's result to SQLite. On restart it resumes unfinished runs from the last completed node. The same flow runs live or against a virtual clock, with a browser editor for building and inspecting flows.

The trading stack, by layer

Bloom and Flow together

LayerWhat runs
Data pipelineGap detection against stored coverage, then fetches under per-account rate limits that honour every window a broker documents at once. Invalid bars and suspected splits trigger bounded re-fetches. Live ticks from each broker's own feed arrive in one shape.
Execution engineOne intent schema, broker adapters behind a trait, and background book sync with exponential backoff that picks up refreshed tokens without a restart.
Risk controlsA day-level governor (loss limit, profit target, trade count, time window) that can halt entries or force liquidation. A final pre-trade guard that checks the raw broker order book, added after a filtering bug silently hid pending orders. Position caps with reconciliation.
BacktestingFlows replay on a virtual clock with a simulated broker. Each trading day can run as an independent, parallel slice. Bloom's Replay broker models latency, spread, slippage, gap-through stops and broker-style rejections.

Mock broker

Broker simulator · April to October 2026

The problem

Markets are closed on weekends and real brokers are a poor place to test failure paths. Rejections, stops falling through and partial volume are hard to trigger on demand.

What I built

A standalone broker with the full order lifecycle, P&L tracking, saved market scenarios, broker-style rejections, and fills capped to a share of traded volume. It plugs into Bloom like any other broker.

Architecture

A Python API over a locked CSV-backed store with a matching engine. A control UI sets prices and scenarios. It can also trade on prices from a separate simulated market feed.

Tech

Python, FastAPI, pytest, React, TypeScript, Playwright.

Slovko

Language-learning app · October 2026

The problem

Every course item produces several kinds of exercise, too many to check by hand. Generated ones can be unfair, offering two right answers or none.

What I built

A Duolingo-style app with lessons, spaced repetition, adaptive difficulty, streaks and speech. A full Slovak course, a Czech starter, and a knowledge course. Guests can use everything, and accounts sync across devices.

Architecture

A Rust server validates course files at startup and serves the API. One web app, with no build step, is wrapped by Capacitor for iOS and Android. Progress lives in the browser and in SQLite, and two devices' saves are merged, not overwritten. A checker generates every exercise for every item, and app builds stop if any is unfair.

Tech

Rust, Axum, SQLite, React 18 with htm, Capacitor, Docker.
